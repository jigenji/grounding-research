## 1. 手法一覧と分類体系

グラウンディング手法を**知識の形式化度**と**システムとの結合方式**で5群に分類する。

| 群 | 分類名 | 含まれる手法 |
|----|--------|-------------|
| **A** | 形式的知識表現 | オントロジー(OWL/RDF/RDFS)、ナレッジグラフ、タクソノミー/統制語彙、スキーマ/データモデル、形式論理/ルールエンジン |
| **B** | 検索・文書ベース | RAG各種、平ドキュメント/フラットファイル、エンベディング検索、構造化プロンプティング |
| **C** | リアルタイム接続・行動系 | ツール利用/Function Calling/MCP、デジタルツイン/シミュレーション、マルチモーダルグラウンディング |
| **D** | 暗黙的・学習ベース | ファインチューニング/RLHF、Constitutional AI/ガードレール |
| **E** | ハイブリッド・新興 | Graph RAG、セマンティックレイヤー/データファブリック、Feature Store、メモリシステム、エージェンティックAI |

## 2. A群: 形式的知識表現

### 2.1 オントロジー（OWL / RDF / RDFS / SKOS）

#### 技術原理
オントロジーは、ある領域の概念・関係・制約を**機械可読な論理形式**で定義する知識表現フレームワークである。

- **RDF（Resource Description Framework）**: 主語-述語-目的語のトリプルでデータを記述。ウェブ上の分散データをグラフとして結合可能
- **RDFS（RDF Schema）**: クラス階層（`rdfs:subClassOf`）やプロパティのドメイン・レンジ定義を追加。軽量な語彙定義に使用
- **OWL（Web Ontology Language）**: 記述論理に基づく表現力の高いオントロジー言語。クラスの等価性、制約（基数制約、値域制約）、推移的関係等を厳密に定義可能。OWL-Lite / OWL-DL / OWL-Fullの表現力階層
- **SKOS（Simple Knowledge Organization System）**: シソーラス、分類体系、タクソノミーなどを軽量に記述。`skos:broader`/`skos:narrower`/`skos:related`で概念間の関係を表現

#### AIグラウンディングにおける役割
- **意味の厳密な定義**: 「顧客」「注文」「製品」等の概念が何を意味し、どう関連するかを形式的に定義し、AIの解釈のブレを防止
- **推論の基盤**: OWL推論器（Pellet, HermiT等）がオントロジーから新事実を自動導出。AIの知識を論理的に拡張
- **相互運用性**: 異なるシステム間で共通語彙を確立し、データサイロを横断した統一的理解を実現
- **OG-RAG（Ontology-Guided RAG）**: オントロジーで検索コンテキストを構造化し、正確な事実の再現率55%向上、正確性40%向上を報告

#### ユースケース
- ライフサイエンス（Gene Ontology、SNOMED-CT等の医療用語体系）
- 金融規制（FIBO: Financial Industry Business Ontology）
- 製造業（IOF: Industrial Ontology Foundry）
- セマンティックウェブ / LinkedData

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **最高**。記述論理に基づく厳密な形式セマンティクス |
| 運用結合度・ガバナンス | **高**。推論器・トリプルストア・SPARQLエンドポイント等の専用インフラが必要。変更管理が重い |
| スケーラビリティ | 低〜中。OWL推論は計算量が大きく、大規模データでは性能課題 |
| 維持コスト | **高**。専門家（オントロジスト）による設計・保守が必要 |

### 2.2 ナレッジグラフ

#### 技術原理
ナレッジグラフは、エンティティ（ノード）とリレーション（エッジ）をグラフ構造で表現する知識表現技術である。

- ノードが実世界の概念・事物（人、場所、組織、製品等）を表し、エッジがそれらの関係を表す
- プロパティグラフモデル（Neo4j等）とRDFトリプルモデル（Wikidata等）の2つの主要パラダイム
- グラフ問い合わせ言語（Cypher, SPARQL, Gremlin）により柔軟な探索が可能

#### オントロジーとの関係
- オントロジーが「**語彙・スキーマ**」（TBox: 用語ボックス）を定義し、ナレッジグラフが「**インスタンスデータ**」（ABox: 主張ボックス）を保持する関係
- 実務上はオントロジーなしのナレッジグラフも多い（プロパティグラフ型）

#### AIグラウンディングにおける役割
- **構造化された文脈の提供**: 「〇〇は△△の子会社で、××業界に属する」等の関係性をAIに明示
- **マルチホップ推論**: 直接繋がっていないエンティティ間の関係を複数ホップで推論可能
- **説明可能性**: グラフのパスやノードに回答を遡及追跡でき、AIの応答根拠を可視化

#### ユースケース
- エンタープライズ知識管理（社内ナレッジベースの構造化）
- 検索エンジン（Google Knowledge Graph）
- レコメンデーション（Amazon, Netflix）
- 不正検知（金融取引ネットワーク分析）
- 医薬品開発（薬剤-疾患-遺伝子の関係ネットワーク）

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **高**。エンティティと関係が明示的に定義される。ただしオントロジーほど論理的には厳密でない場合も |
| 運用結合度・ガバナンス | **中〜高**。グラフDB（Neo4j等）の運用が必要。スキーマ進化の管理が課題 |
| スケーラビリティ | 中〜高。分散グラフDB（Neptune, JanusGraph）で大規模対応可能だが、複雑なクエリはコスト増 |
| 維持コスト | **中〜高**。エンティティ抽出・関係構築のパイプライン運用。品質管理が継続的課題 |

---

### 2.3 タクソノミー / 統制語彙

#### 技術原理
- **タクソノミー**: 階層的な「is-a」関係で概念を分類する木構造。例: 生物学的分類体系、製品カテゴリ
- **統制語彙（Controlled Vocabulary）**: ドメインで使用する用語を事前に定め、同義語・曖昧性を排除する用語集
- タクソノミーはオントロジーのサブセットとみなせるが、関係の種類が限定的（主に階層関係のみ）

#### AIグラウンディングにおける役割
- **分類の一貫性**: AIの出力カテゴリをタクソノミーに制約し、分類のブレを防止
- **検索の精度向上**: 「自動車」で検索したときに「車」「クルマ」もヒットするように同義語を管理
- **ファセット検索**: 複数の分類軸（価格帯×ブランド×用途等）で結果を絞り込み

#### ユースケース
- Eコマースの商品分類（GS1、UNSPSC）
- 図書館情報学（LC Subject Headings）
- コンテンツ管理システムのタグ体系
- 企業内文書の分類

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **中〜高**。階層関係は明示的だが、オントロジーほど多様な関係を表現しない |
| 運用結合度・ガバナンス | **中**。比較的軽量に導入可能。変更管理はシンプル |
| スケーラビリティ | 高。階層構造は効率的にスケール |
| 維持コスト | **低〜中**。ドメイン専門家による定期的レビューが必要だが、オントロジーほど高くない |

---

### 2.4 スキーマ / データモデル

#### 技術原理
- **JSON Schema / XML Schema**: データの構造・型・制約を形式的に定義。APIのリクエスト/レスポンス形式を規定
- **データベーススキーマ**: テーブル定義、外部キー制約、CHECK制約等でデータの整合性を保証
- **GraphQL**: 型システムによる厳密なデータモデルとクエリ言語。クライアントが必要なデータ形状を宣言的に指定

#### AIグラウンディングにおける役割
- **構造化出力の保証**: JSON Schemaに準拠した出力をAIに強制し、下流システムとの統合を確実に
- **Text-to-SQL**: データベーススキーマをAIに提示し、自然言語クエリからSQL文を生成。スキーマがグラウンディングの直接的な根拠
- **API設計**: ツール利用/MCP時のインターフェース仕様としてスキーマがAIの操作可能範囲を規定

#### ユースケース
- AI出力のバリデーション
- Text-to-SQL / Text-to-API
- データパイプラインの品質保証
- AIアプリケーションの入出力仕様定義

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **中〜高**。構造・型は厳密に定義されるが、ビジネス上の「意味」は別途定義が必要 |
| 運用結合度・ガバナンス | **高**。システム間のインターフェース契約として強い結合。バージョニングと互換性管理が重要 |
| スケーラビリティ | 高。標準的な技術インフラでスケール |
| 維持コスト | **中**。スキーマ進化の管理が必要だが、ツール支援が充実 |

---

### 2.5 形式論理 / ルールエンジン

#### 技術原理
- **Prolog / 論理プログラミング**: 述語論理に基づく宣言型プログラミング。事実と規則を定義し、自動推論エンジンが問い合わせに回答
- **SWRL（Semantic Web Rule Language）**: OWLオントロジーにIF-THENルールを追加。「もし顧客が60日以上未払いなら、アカウントステータスを延滞にする」等
- **ビジネスルールエンジン（Drools等）**: 業務ルールを宣言的に定義し、意思決定の自動化とコンプライアンス保証に使用

#### AIグラウンディングにおける役割
- **推論の制約**: AIの出力をビジネスルールに照合し、規則違反を検出・防止
- **ニューロシンボリック統合**: LLMの柔軟な言語処理と論理推論の厳密性を組み合わせる研究分野
- **監査可能な意思決定**: ルールの発火履歴から意思決定過程を完全に再現可能

#### ユースケース
- 金融規制コンプライアンス
- 保険の引受判断
- 医療診断支援（臨床意思決定ルール）
- 税計算・法的推論

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **最高**。述語論理/命題論理に基づく完全に形式的な意味定義 |
| 運用結合度・ガバナンス | **最高**。ルールエンジンがシステムの意思決定フローに直接組み込まれる |
| スケーラビリティ | 低〜中。ルール数の増加でパフォーマンスと保守性が低下 |
| 維持コスト | **高**。ルールの矛盾検出・優先度管理が複雑。ドメイン専門家の継続的関与が必要 |

## 3. B群: 検索・文書ベース

### 3.1 RAG（Retrieval-Augmented Generation）

#### 技術原理
RAGはLLMの「外部記憶」として機能し、クエリ時に関連文書を動的に検索してコンテキストに注入するアーキテクチャである。

**パイプラインの4段階:**
1. **取り込み・インデキシング**: 文書をチャンクに分割 → エンベディング生成 → ベクトルDBに格納
2. **検索（Retrieve）**: クエリをエンベディング化 → ベクトル類似度検索 / ハイブリッド検索でTop-K候補を取得
3. **リランキング**: クロスエンコーダで候補を再評価し、真の関連度でソート
4. **生成（Generate）**: 検索コンテキスト付きプロンプトでLLMが回答を生成

**主要バリアント:**
| バリアント | 特徴 | 適用場面 |
|-----------|------|---------|
| Naive RAG | 単純な3ステップ（検索→生成） | FAQ、限定スコープの質問応答 |
| Advanced RAG | リランキング、クエリ書き換え、ハイブリッド検索 | 本番チャットボット、中規模ナレッジベース |
| Modular RAG | 各コンポーネントを独立モジュール化 | エンタープライズ、多データソース統合 |
| Graph RAG | エンティティ・関係のグラフで検索 | 複雑な関連性推論、マルチホップQA |
| Agentic RAG | 自律的エージェントが検索戦略を動的決定 | リアルタイム分析、複雑なマルチドメイン |

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **中〜高**。Graph RAGでは高い形式性。Naive RAGでは元文書の構造に依存 |
| 運用結合度・ガバナンス | **中〜高**。ベクトルDB・インデキシングパイプラインとの結合。ガバナンスはアーキテクチャレベルで設計が必要 |
| スケーラビリティ | **高**。クエリ時に関連データのみ検索するため本質的にスケーラブル |
| 維持コスト | **中〜高**。73%のエンタープライズRAGシステムが予算超過という報告あり |

---

### 3.2 平ドキュメント / フラットファイル

#### 技術原理
Markdown、PDF、テキストファイル、プロンプトテンプレート等をそのままLLMのコンテキストウィンドウに注入する最もシンプルなグラウンディング手法。

**代表例:**
- **CLAUDE.md / システムプロンプト**: プロジェクトの規約・コンテキストを自然言語で記述し、AIセッション開始時に毎回ロード
- **SKILL.md**: スキル定義ファイル。呼び出し時にコンテキストに展開
- **社内文書**: 規定、マニュアル、FAQ等をそのまま注入

**Markdownが優位な理由:**
- 見出し・リスト・テーブル等で構造を表現でき、LLMが関係性を識別しやすい
- JSON/XML/HTMLより軽量でトークン効率が高い
- LLMの訓練コーパスに大量に含まれており、構造化された指示の理解が良好

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **低〜中**。自然言語ベース。見出し等で部分的に構造化されるが、形式的セマンティクスは限定的 |
| 運用結合度・ガバナンス | **低**。ファイルシステムに配置するだけ。Git等でバージョン管理可能。特殊インフラ不要 |
| スケーラビリティ | **低〜中**。コンテキストウィンドウの制約。大規模ではRAGへの移行が必要 |
| 維持コスト | **最低**。テキストエディタで編集可能。正確性の維持は人間の責任 |

---

### 3.3 エンベディングベース・セマンティック検索

#### 技術原理
テキストを密な数値ベクトルに変換し、ベクトル空間上の近傍検索で意味的に類似したコンテンツを取得する。

- **密ベクトル**: セマンティックマッチングに優れる（同義語・パラフレーズ・概念的類似性を捕捉）
- **スパースベクトル**: 正確なキーワードマッチングに優れる（BM25系）
- **2025-2026年のコンセンサス**: 密ベクトル + BM25のハイブリッド検索がRAG精度ベンチマークを倍増

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **中**。意味がベクトル空間に数学的に符号化されるが、人間が直接解釈不能（ブラックボックス） |
| 運用結合度・ガバナンス | **中〜高**。ベクトルDB・エンベディングモデルとの結合。モデル変更時に全インデックス再構築が必要 |
| スケーラビリティ | **高**。ANN（近似最近傍）アルゴリズムにより大規模データでも効率的検索 |
| 維持コスト | **中**。インフラ費用、モデル更新時の再インデキシング |

---

### 3.4 構造化プロンプティング

#### 技術原理
プロンプトの設計・構造を通じてLLMの応答を制御するインコンテキスト手法群。

| 手法 | 原理 | 効果 |
|------|------|------|
| Chain-of-Thought (CoT) | 中間推論ステップを明示的に生成させる | 複雑な推論タスクの精度向上 |
| Few-shot | 入出力の実例を提示 | フォーマット・スタイル・振る舞いの制御 |
| Self-Consistency | 複数推論パスを生成し、最も一貫した回答を選択 | CoT推論の信頼性向上 |
| Tree-of-Thought | 複数の推論ラインを並列に生成・探索 | 探索的問題解決の改善 |
| 構造化出力指定 | JSON/YAML等の出力フォーマットを指定 | 下流システムとの統合性保証 |

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **中**。自然言語指示で意味を伝達。構造化出力指定で部分的に形式化 |
| 運用結合度・ガバナンス | **最低**。プロンプトのみで完結。外部システム結合不要 |
| スケーラビリティ | **中**。テンプレート再利用可能だが、コンテキストウィンドウを消費 |
| 維持コスト | **最低**。テキスト編集のみ。ただしモデル更新時に再検証が必要 |

---

## 4. C群: リアルタイム接続・行動系

### 4.1 ツール利用 / Function Calling / MCP

#### 技術原理
LLMがリアルタイムで外部APIやサービスにアクセスし、最新情報に基づいて応答をグラウンディングする。

- **Function Calling**: LLMが関数呼び出しのJSON仕様を出力し、ホストシステムが実行して結果を返す
- **MCP（Model Context Protocol）**: Anthropicが2024年に導入したオープン標準。N×Mのデータ統合問題をN+Mに削減
  - JSON-RPC 2.0 over WebSocketによる双方向チャネル
  - ツールの自己記述化・動的発見
  - 2025年12月にLinux Foundation傘下のAgentic AI Foundation(AAIF)に寄贈。事実上の業界標準

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **高**。APIスキーマ・関数シグネチャで意味が形式的に定義 |
| 運用結合度・ガバナンス | **最高**。外部サービスとのリアルタイム接続。セキュリティリスクも最大 |
| スケーラビリティ | **高**。MCPのN+Mモデルにより統合の複雑さが線形にスケール |
| 維持コスト | **中**。MCPサーバーの構築・維持、API変更への追従 |

### 4.2 デジタルツイン / シミュレーション

- **ハイブリッドモデリング**: AIと物理ベースシミュレーションを組み合わせ、AI予測が物理法則に基づくことを保証

- 半導体ファブ設計（TSMC）
- 地球科学（カスケード沈み込み帯のデジタルツイン）

## 5. D群: 暗黙的・学習ベース

### 5.1 ファインチューニング / RLHF

#### 技術原理
訓練データを通じてモデルのパラメータ自体に知識や振る舞いを「焼き込む」暗黙的グラウンディング。

- **ファインチューニング**: ドメイン固有データでモデルパラメータを調整。スタイル・トーン・専門用語の習得
- **RLHF**: 人間の選好フィードバックでモデルを調整。望ましい出力を直接最適化
- **DPO（Direct Preference Optimization）**: RLHFパイプラインを簡素化した手法

**RAGとの役割分担（2025年のベストプラクティス）:**
- ファインチューニング = 行動の形成（スタイル、トーン、フォーマット）
- RAG = 事実のグラウンディング（最新知識、検証可能な情報）

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **最低**。知識がモデルの重みに暗黙的に符号化。参照・検証不可能なブラックボックス |
| 運用結合度・ガバナンス | **低〜中**。訓練後はモデル単体で動作。ただし訓練データ→出力の追跡が極めて困難 |
| スケーラビリティ | **低〜中**。ドメインごとに別モデルの訓練が必要な場合は非効率 |
| 維持コスト | **高**。GPU/TPUコスト、定期的再訓練、テラバイト規模のデータセット管理 |

---

### 5.2 ガードレール / Constitutional AI / アラインメント

#### 技術原理
AIの行動を安全かつ信頼できる範囲に制約する手法群。

- **ガードレール**: モデルを変更せずに外部フィルターとして機能。入力フィルタリング・出力検証の多層構造
- **Constitutional AI（Anthropic提唱）**: 自然言語の原則リスト（「憲法」）に基づきモデルを訓練。モデルが自身の出力を批評・改善
- **RLHF**: 人間フィードバックによる行動アラインメント
- **COCOA（EMNLP 2025）**: 憲法とAIモデルを共進化させるフレームワーク

#### 評価
| 次元 | 評価 |
|------|------|
| 意味の明示度・形式性 | **中〜高**。ガードレールのルールは明示的。ConstitutionalAIの原則は自然言語だが構造化されている |
| 運用結合度・ガバナンス | **高**。AIシステムの出力パイプラインに直接組み込まれる。監査可能性が高い |
| スケーラビリティ | 中〜高。ルール数の増加で複雑性は増すが、自動合成技術で改善 |
| 維持コスト | **中**。ルール・原則の定期的レビューと更新が必要 |

## 6. E群: ハイブリッド・新興手法

### 6.1 Graph RAG

RAGとナレッジグラフを統合し、マルチホップ推論とハルシネーション削減を実現。

- **MicrosoftのGraphRAG実装**: LLMでエンティティ抽出 → グラフ構築 → Leidenアルゴリズムでコミュニティ検出 → コミュニティ要約のMap-Reduce処理
- **性能**: マルチホップQAの再現率+6.4ポイント、ハルシネーション18%削減、包括性・多様性70-80%勝率
- **2026年の動向**: LinearRAG（ICLR 2026採択）、MCPによるGraphRAGデータソース標準化

### 6.2 セマンティックレイヤー / データファブリック

- **セマンティックレイヤー**: 複雑なデータをビジネスフレンドリーな用語と統一メトリクスに変換する抽象化層
- **データファブリック**: クラウド/オンプレ/SaaS全体のデータをデータ移動なしで統合する技術レイヤー
- **データメッシュ**: 分散型データオーナーシップとドメインベースのデータプロダクト
- **Microsoft Fabric IQ（2025年）**: オントロジーを通じてAIに精密なセマンティックバックボーンを提供

### 6.3 Feature Store

MLOpsインフラの構成要素として、特徴量の保存・管理・変換・提供を一元化。

- **Feast（OSS）**: プラガブルアーキテクチャ、Linux Foundation傘下
- **Tecton（エンタープライズ）**: 宣言型DSL、Databricks統合
- **Hopsworks**: ガバナンス特化、規制産業向け
- **AIグラウンディングとの関係**: ベクトル埋め込みの提供レイヤーとしてRAGを支援し、AIアプリケーションのグラウンディングレイヤーとして機能

### 6.4 メモリシステム

LLMの固定コンテキストウィンドウを超えた持続的記憶を提供。

- **MemGPT/Letta**: OSの階層的メモリ管理にインスピレーション。コンテキストウィンドウ=RAM、外部ストレージ=ディスクの対応
- **認知科学の4分類**: ワーキングメモリ（現在の会話）、手続き的記憶（システムプロンプト）、意味記憶（蓄積された事実）、エピソード記憶（過去の対話ログ）
- **時間的知識グラフ**: Zep/Graphitiがエピソード記憶と意味記憶を融合

### 6.5 エージェンティックAI

全てのグラウンディングコンポーネントを統合するオーケストレーション層。

**合成パターン:**
| パターン | 構成 | 効果 |
|---------|------|------|
| Graph RAG | RAG + ナレッジグラフ | マルチホップ推論 |
| OG-RAG | オントロジー + RAG | 正確性40%向上 |
| エージェンティックシステム | ツール利用 + メモリ + 計画 | 目標指向型タスク実行 |
| Physical AI | デジタルツイン + AI + 物理シミュレーション | 現実世界でのAI行動 |
| 信頼可能なAI | グラウンディング + ガードレール + メモリ | 監査可能なエンタープライズAI |
